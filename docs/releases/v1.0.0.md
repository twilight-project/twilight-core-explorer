## What this release is

**Twilight Core Explorer v1.0.0 is the first release**: the indexer, the public API and the web explorer
as built and run so far, now under a version number.

From this release on, the public API (`/api/v1/*`, 48 paths, described by `docs/reference/openapi.json`
and browsable at `/docs`) is a **stable contract**. A breaking change to it means a new major version.
Additive changes (new paths, new fields) are minor releases.

The explorer runs against **Twilight testnet**. Twilight Core is a pre-1.0 public testnet, and this
explorer has not been externally audited.

There are no binaries. The explorer is a service: operators build it from this tag with Docker
(runbook §13), and a running instance proves which release it is by reporting the tag and commit at
`GET /api/v1/status` → `data.build`.

## What's in it

- **Indexer.** Blocks, transactions, messages, events and accounts from CometBFT RPC + Twilight REST
  into Postgres, decoded from the chain's protobuf descriptors. Everything else is derived from these
  rows and can be rebuilt from them.
- **CoreSlot semantics.** Metadata, lifecycle, payout, params, key rotation and a temporal consensus
  map. Ambiguous history becomes a recorded `ProjectionFailure`, never a guess.
- **Liveness and network health.** Signature ingestion and attribution, proposer attribution, missed
  evidence, liveness summaries, per-slot health and a network halt-risk snapshot.
- **Rewards, mining and supply.** Epochs, claims, entitlements, mining settlements, and sampled
  rewards/balance/supply snapshots (always labelled with their sample height and age). Read-only:
  claiming stays CLI-only.
- **Operators.** Profile pages (overview, details, data, authentication), the operator's own feed
  sampled as *attested* data behind a privacy guard, and **independent draw verification**, which
  re-derives each selection draw from chain data and shows *verified*, *mismatch* or *unverifiable*,
  naming its limits.
- **Web explorer.** Next.js 16, consuming only the public API, with explicit freshness states (no
  fabricated zeros), accessible tables and the Twilight brand theme.

The full list, by capability, is in [`CHANGELOG.md`](../../CHANGELOG.md).

## Verification

- **Release gate:** `npm run rc-check`, including the live tier (`RC_LIVE=1`). A ~2,500-block localnet
  soak ran green with 53 checks: block/tx cursor walks match the database, 0 unresolved projection
  failures, freshness present.
- **This commit, on Node 24 (the runtime of the images and CI):** typecheck, lint, the API, indexer,
  web and chain-client test suites, both OpenAPI drift checks, `next build`, and the static route guards
  (no `/cosmos/staking|gov|mint|distribution` routes) all pass.
- **Review:** each part was reviewed before merge, adversarially, with the draw verifier checked rule by
  rule against the reference Go implementation and re-probed with the attacks that found its earlier
  bugs.
- **Dependencies:** 0 open Dependabot alerts at release.

## Upgrading and deploying

This is the first release, so there is nothing to upgrade from. To run it, deploy the `v1.0.0` tag with
runbook §13 (`docs/operations/devnet-deploy-runbook.md`). The deploy script refuses anything that isn't
a `v*` tag on `main`, refuses a dirty working tree, and stamps the tag into the build.

New settings since the last untagged deployment:
- `EXPLORER_DOMAIN`: the public hostname Caddy serves. The canonical domain is `explorer.twilight.org`.
- `NEXT_PUBLIC_SITE_URL`: the canonical origin for share cards, sitemap and robots (build time;
  defaults to `https://explorer.twilight.org`).
- `API_TRUST_PROXY`: which peers may set the client address for rate limiting. Compose defaults to
  `loopback,uniquelocal`; set it to `false` if the API is ever exposed directly.

There are no database migrations beyond those already applied by the `migrate` service.

## Known limitations

- The devnet soak is still deferred (Issue #41); the soak so far is localnet.
- Postgres backups with a tested restore, and rotating the default database password, are operational
  tasks on the deployment host.
- Draw verification does not yet check the single-anchor rule, and compares only the selection rate and
  max-selected with the chain policy. The verification badge states both limits.
- Rate limiting is in-process, so it holds per instance only.
